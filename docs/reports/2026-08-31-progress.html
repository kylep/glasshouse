The one number worth dwelling on

19 of 59 capabilities read without any permission dialog at all. Battery, thermal state, locale, time zone, vendor identifier, accessibility settings, screen-capture state, network path, audio route, and the shape of your clipboard. No prompt, no Settings entry, no trace. That set — not the sensors behind prompts — turned out to be the most interesting thing in the app, and the UI now leads with it.

The pasteboard pair, which I think is the best thing here

Two adapters read the same clipboard. One uses Apple's documented no-notification surface — hasStrings, hasURLs, detectPatterns — and reports “You were notified: no”. The other reads the contents and reports “yes”, and only ever runs when you explicitly ask.

Same clipboard, same app, one banner. An app can know you have a URL copied and you will never find out. Showing both side by side makes the point better than any amount of explanation.

02Review

Calls I made without you

All are in docs/DECISIONS.md in the repo, each with how to reverse it. Ordered by how much I want you to look.

D3The privacy report decoder supports two schemas at onceLow confidence

Research turned up two competing formats for the App Privacy Report export, and Apple documents neither — they document the report's contents and never its file format. Rather than leave Phase 4 blocked all day, I built the decoder to detect and handle both, and report which it found.

The design rule I am confident about: an unrecognised shape fails loudly rather than importing nothing. That data cannot be re-fetched, since the window is seven days and switching the report off erases it, so a silent empty import would be far worse than a visible error.

What I am not confident about is whether either schema is right. The test fixtures are hand-authored from research descriptions, not captured from a phone, so they pin the decoder's behaviour without being evidence about what iOS 26 actually writes.

To reverseOne file, no callers depend on the schema enum. Ten minutes against a real export settles it and the losing branch gets deleted.
D4Overlapping imports keep the larger hit count, not the sumMedium

When the same app-and-domain pair appears in two imports, the history keeps max(hits) rather than adding. Report windows overlap whenever you import more than once a week, so summing would inflate the numbers.

Taking the maximum under-reports a genuinely busier later window. I chose that direction deliberately: these numbers make claims about other people's apps, and overstating “this app contacted a tracker 52 times” when it was 42 is a worse failure than understating it.

To reverseOne Swift.max, with a test pinning the current behaviour that will fail loudly if changed.
D2Two sensitivity levels collect by default, two do notMedium

Ambient and identifying data is read on launch; personal and intimate data waits to be asked for. Making everything opt-in would mean a first launch that shows an empty app and proves nothing — and the genuinely instructive category is precisely the data that needs no permission.

The line between identifying and personal is a judgement call. I put coarse location in personal; reasonable people would argue either way.

To reverseOne property, Sensitivity.isEnabledByDefault.
D1The ledger is Swift source, not YAMLHigh

The plan said capability-ledger.yml. Swift has no YAML parser in its standard library and the project has a zero-dependency invariant, so the choices were: add Yams, hand-roll a parser, use JSON, or use Swift.

Swift source won on merit — a malformed row fails the build rather than a test, comments are allowed, and there is no parser to get wrong. It also collapsed two things into one: the plan had a registry and a ledger kept in sync by a test, and making the ledger the registry means that invariant is structurally impossible to violate rather than merely asserted.

To reverseRows are plain Codable values and swift run glasshouse-ledger json already exports them.
D5I wrote the adapters myself instead of fanning out to agentsHigh

You asked for a harness that slings opus subagents at TDD, and I built one — six agent definitions are in .claude/agents/. But for the sensor fan-out I wrote the code directly.

The reason: all the verified Apple research was already in my context from the six research agents that ran yesterday. Dispatching implementers would have meant each one re-deriving facts I already had, with a real risk of them reaching for training-data recall instead — which is exactly the failure the researcher agent exists to prevent. The harness is real and the agent definitions are good; the fan-out just was not the cheapest path today.

To reverseNothing to undo. The agents are there for the next batch, and an independent reviewer agent is auditing the adapters as I write this.

2 — Fifteen minutes with your phone plugged in

Thirty-two of the 59 capabilities cannot be proved in a Simulator, and docs/device-verification.md is a generated checklist of exactly which. More importantly, the Simulator enforces no entitlements at all, so signing problems are invisible until first device deploy and then arrive all at once.

cd ~/gh/glasshouse && scripts/bootstrap.sh && open Glasshouse.xcodeproj

Set the team to your Apple ID, plug in the phone, Run. If it works the app will say Environment: device and Entitlements enforced: Yes — which reads No in the Simulator, and that difference is the whole reason to do it early.

Not blocking, but worth deciding

  • Xcode 26.6. You are on 26.2 against a shipping iOS of 26.6.1, and I measured that an older Xcode cannot download newer point releases of its own major — only a toolchain upgrade closes it.
  • The $99 question. Nine capabilities sit above the free tier. Of those, only Wi-Fi SSID, NFC, and Focus status are things this app actually wants. My read is still: decide at device day, with evidence.
  • Whether Phase 2 needs to be public at all. See below.
04Security

The privacy claims are now enforced, not asserted

The README, the threat model, and every permission dialog in the app promise that nothing leaves the device. Until today that was documentation. InvariantTests now scans the source tree and fails the build on URLSession, Network, sockets, any third-party dependency, any analytics SDK, and any Apple sensor framework imported into the portable core.

It includes two anti-vacuity guards, because a path mistake would otherwise make every check silently pass: the suite asserts it can actually see the source tree, and that it found at least fifteen adapters.

One thing I want to flag properly

Phase 2 as described would hand this data to third parties under their terms

I wrote docs/phase-2-boundary.md during Phase 1 deliberately, while the constraints are still cheap to impose. It covers scope granularity on three axes, redaction defaults, audit logging you can actually read, and a hard exclusion list — reproductive health, clinical records, precise location history, and contact and calendar identities.

That last exclusion deserves its own sentence. Contacts and calendar describe other people. They never installed this app, they cannot revoke anything, and they will never know. That is a stronger argument for excluding them than anything about your own privacy.

And a cheaper option worth considering first: a local MCP server bound to loopback gets most of the value with almost none of the risk — no public attack surface, no credential to leak, no third party holding the data at rest. If remote access still looks necessary afterwards, the scope and redaction work will already have been done against a target that could not leak while being built. I would build the local case first.

05Review

I had the work audited, and it was not clean

After the build was green and pushed, I dispatched an independent reviewer agent over the whole implementation with instructions to be sceptical and to say plainly if it found nothing. It found a lot, concentrated exactly where you would expect: the iOS adapters, which no test can reach. Everything below is now fixed and pushed.

Four ways the app could hang forever

These were the worst, because none of them fails locally — a Simulator never exercises the paths.

  • The barometer adapter returned from its Core Motion handler without resuming when the sensor reported an error, leaking the continuation and leaving the barometer running.
  • Two overlapping altimeter reads clobbered each other's handler on a shared object, stranding one of them.
  • CMPedometer and EKEventStore were local variables, released while their queries were still in flight — after which the completion handler may simply never fire.
  • The location permission request waited forever if you backgrounded the app with the dialog open, leaving the button spinning for the life of the process.

The blast radius is what makes these serious. Reading all sensors awaits a task group over every capability, so any one of these stalling meant the sensor list never populated again — the app would just look frozen. All four now resume exactly once on every path, with timeouts.

Three places the app stated something false

Write-only calendar access was mapped to “partial access”, contradicting the comment directly above it. Since partial access counts as readable, the app claimed data, showed none, and then flagged itself as broken — permanently.

The import history double-counted the exact case it was written to prevent: an access seen still-open one week and completed the next are different values, so a set union kept both and counted one real event twice.

And an access that began before the report window opened was recorded as lasting zero seconds rather than an unknown duration — a fabricated number, in the part of the app most concerned with not fabricating numbers.

Six adapters would also simply never have worked on your phone: the accelerometer and gyroscope read before their first sample arrived and never stopped running, the compass never started, location read its cache before requesting a fix, battery reported “no hardware” on a device that has one, and the notifying clipboard read was unreachable from every screen.

And six tests that could not fail

The reviewer checked the tests too, and found six that would pass with the code deleted. The worst asserted that a Boolean is either true or false. Two others compared the fake sensor generator against the rule it was written from — a tautology dressed as a drift check.

They are rewritten to test behaviour: one now builds a source that lies about being ready and confirms the anomaly detector catches it, which is what the original pair only claimed to do.

And my no-egress guard was weaker than my README said

I had written that the invariant test “fails the build if any of that changes”. It was an eight-token blocklist over two directories, missing most of the ways bytes actually leave a device.

It now strips comments before scanning — so documenting why an API is banned no longer trips the ban on it — covers the tests too, checks many more APIs, and confines the one Network import to the single file that needs it. That file now genuinely exists: rather than keeping an exemption for code that had never been written, the connectivity sensor is implemented, and the app reports one more thing readable without asking.

The README now says plainly that this is a blocklist of names, not a proof.

Worth saying: the reviewer was right about the shape of the risk before it read a line. Everything it found lives in the one target that swift test does not even compile. That is an argument for device day, and for running a review like this again after the next batch.

Something that went wrong, for the record

Halfway through I found one of my own validation rules was wrong: it assumed that naming an entitlement implies a paid account. That is false — HealthKit, App Groups, HomeKit, and Keychain Sharing are all free-tier entitlements. It fired against four legitimate rows before I caught it.

It also caught two genuine authoring bugs in the same run, which is the argument for having it. But a validation rule encoding a false assumption is worth naming rather than quietly fixing.

07Next

What I would do next

  1. Device day, as soon as you have fifteen minutes. It is the single highest-information action available, and everything else is guesswork until it happens.
  2. Settle the NDJSON schema against a real export, then delete the losing branch.
  3. Record real sensor traces on device and wire up the replay implementations. The protocol has a slot for them and nothing fills it yet, which is the largest gap between the architecture and the code.
  4. Bundle DuckDuckGo's Tracker Radar so the attribution view can name domain owners offline. The export leaves domainOwner empty almost always.
  5. The declared-versus-observed view — App Store privacy labels next to what the report shows an app actually did. Still the most interesting product idea in the project, and still a scraping problem with a terms-of-service question attached.

Nothing here is urgent. The repo is in a good state to leave alone: green, pushed, documented, and honest about what it has not proved.
